# ثبت دستی عملکرد محتوای منتشرشده

> وضعیت: **پیاده‌سازی‌شده در نسخهٔ ۰٫۲۰٫۰.** هیچ اتصالی به پلتفرم‌ها نیست؛ ادمین آمار را از خود پلتفرم می‌خواند و وارد می‌کند. این داده پیش‌نیاز «حلقهٔ یادگیری» (docs/27 ایدهٔ ۵) است و تا وقتی ثبت نشود آن حلقه داده ندارد.

## ۱. مدل داده

`ContentMetric` (migration `20261013140000_content_metrics`، جدول تازه، افزایشی):

| فیلد | توضیح |
|---|---|
| `measuredAt` | روزی که عددها خوانده شد (تاریخ میلادی، بدون ساعت) |
| `views`، `likes`، `comments`، `shares`، `saves`، `clicks`، `conversions` | عدد صحیح ≥ ۰، همه اختیاری (`null` = نامعلوم) |
| `revenue` | درآمد حاصل از پست، به واحد پول کسب‌وکار (عدد اعشاری ≥ ۰) |
| `note`، `createdById` | یادداشت و ثبت‌کننده |

- **یک خوانش برای هر محتوا و هر روز** (`@@unique([contentId, measuredAt])`). ثبت دوبارهٔ همان روز آن روز را **جایگزین** می‌کند و عددهایی که ننوشته‌اید `null` می‌شوند.
- عددها **تجمعی** فرض می‌شوند (همان‌طور که پلتفرم نشان می‌دهد)؛ جدیدترین خوانش وضعیت فعلی پست است.
- هر خوانش دست‌کم یک عدد دارد.
- با حذف محتوا خوانش‌ها هم حذف می‌شوند.

## ۲. قواعد

- فقط برای محتوای **منتشرشده** (`publishedAt` پر) ثبت می‌شود، وگرنه `409`. محتوای منتشرشده برای ویرایش یخ‌زده است ولی خوانش‌هایش نه: آن‌ها پست را توصیف می‌کنند و عوضش نمی‌کنند.
- تاریخ خوانش نمی‌تواند پیش از روز انتشار یا بیش از فردا باشد (`400`).
- دسترسی مثل خود محتواست: `@TopicScoped('content')` و برای ویرایش/حذف یک خوانش `@TopicScoped('metric')` (در `common/access.ts`). نقش بیننده نمی‌نویسد.
- هر تغییر ممیزی می‌شود (`content.metric`، `content.metric_bulk`، `content.metric_update`، `content.metric_delete`).

## ۳. API

| متد | مسیر | توضیح |
|---|---|---|
| GET | `/contents/:id/metrics` | `{ items, summary }`؛ جدیدترین اول |
| POST | `/contents/:id/metrics` | یک خوانش (`measuredAt` پیش‌فرض امروز)؛ جایگزین همان روز |
| POST | `/contents/:id/metrics/bulk` | `{ rows: [...] }` تا ۳۶۶ ردیف؛ همه اول بررسی می‌شوند و با یک خطا هیچ‌کدام ذخیره نمی‌شود؛ روز تکراری در یک درخواست `400` |
| PATCH | `/content-metrics/:id` | تغییر بخشی از عددها؛ نباید خوانش را بی‌عدد کند |
| DELETE | `/content-metrics/:id` | حذف |

همهٔ مسیرها `{ items, summary }` را برمی‌گردانند. `summary` (تابع `summarizeMetrics`):

- `latest`: جدیدترین خوانش.
- `engagement` = لایک + کامنت + اشتراک + ذخیرهٔ جدیدترین خوانش (فقط عددهای معلوم؛ `null` اگر هیچ‌کدام نباشد).
- `engagementRate` = engagement ÷ views و `clickRate` = clicks ÷ views؛ `null` بدون بازدید. شاخص تقریبی است، نه معیار صنعتی.

## ۴. ورود گروهی (چسباندن جدول)

دکمهٔ «چسباندن جدول» در کارت عملکرد. تابع `parseMetricsTable` (در مرورگر، پیش از ارسال):

- جداکننده خودکار شناخته می‌شود: Tab، `;`، `؛`، `,` یا `،`.
- ردیف اول نام ستون‌هاست، فارسی یا انگلیسی: `تاریخ`، `بازدید`، `لایک`، `کامنت`، `اشتراک‌گذاری`، `ذخیره`، `کلیک`، `فروش`، `درآمد`، `یادداشت` (و `date`، `views`، `likes`، `comments`، `shares`، `saves`، `clicks`، `conversions`، `revenue`، `note`).
- ارقام فارسی، جداکنندهٔ هزارگان و پسوند `k` و `m` (مثل `12.5k`) پذیرفته می‌شود؛ `-` یعنی نامعلوم.
- **تاریخ فقط میلادی** (`2026-10-01` یا `2026/10/01`، با ارقام فارسی هم) است. تاریخ شمسی با پیام روشن رد می‌شود، چون طبق قرارداد پروژه مبدل شمسی دست‌نویس نداریم (فقط `Intl` برای نمایش).
- ستون تاریخ نداشتن با «تاریخ ردیف‌های بدون تاریخ» جبران می‌شود.
- ردیف خراب با شمارهٔ خط گزارش می‌شود و ردیف‌های درست ثبت می‌شوند؛ اگر یک روز دو بار بیاید خط آخر برنده است و کاربر مطلع می‌شود.

## ۵. محدودیت‌ها

- فقط تعامل **کل پست** ثبت می‌شود؛ نه به‌تفکیک نظر یا دنبال‌کننده (و طبق CLAUDE.md هرگز دادهٔ کامنت و دنبال‌کننده ذخیره نمی‌شود).
- نرخ تعامل نسبت به بازدید است؛ برای پلتفرمی که بازدید نمی‌دهد (مثلاً بعضی کانال‌های پیام‌رسان) `null` می‌ماند.
- هنوز تحلیلی روی این داده نیست؛ مصرف‌کنندهٔ بعدی «حلقهٔ یادگیری» است (نیاز به حجم کافی پست، docs/27 بخش ۶).
- در فهرست محتواها ستون عملکرد نیست؛ فقط در صفحهٔ هر محتوا دیده می‌شود.
