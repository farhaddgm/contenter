# کلید API شخصی و API عمومی v1

> وضعیت: **پیاده‌سازی‌شده** (گام ۴۱ از [29-roadmap-50-steps.md](29-roadmap-50-steps.md)). بدون AI. **تأیید نهایی با کلید ممکن نیست**؛ فقط چند مسیر خواندنی و «درخواست پیش‌نویس» کلید می‌پذیرند.

برای وصل کردن Contenter به n8n، Zapier یا اسکریپت خود تیم، نباید توکن مرورگر قرض گرفت. هر کاربر در صفحهٔ **حساب کاربری** کارت «کلیدهای API شخصی» دارد.

## کلید چیست

- قالب: `ctk_` + ۸ نویسهٔ هگز (شناسهٔ پیدا کردن ردیف) + `_` + ۴۳ نویسهٔ تصادفی (۲۵۶ بیت). مثال: `ctk_0123abcd_…`.
- کل کلید **فقط یک بار** هنگام ساخت نمایش داده می‌شود؛ در پایگاه داده فقط SHA-256 آن و پیشوند (`ctk_0123abcd`) است. (کلید ۲۵۶ بیت تصادفی است، پس هش سریع کافی است و به `SecretBox` نیازی نیست.) کلید و هش هرگز به لاگ ممیزی نمی‌روند و `sanitize()` لاگ تعاملات هدرهای `authorization` را سانسور می‌کند.
- مقایسه با `timingSafeEqual`؛ کلید ناشناخته همان‌قدر هزینه دارد که کلید غلط و هر دو فقط `401 Invalid API key` می‌دهند.
- جدول `ApiKey` (migration `20261014140000_api_keys`، افزایشی): `userId`، `name`، `prefix` یکتا، `hash`، `scopes`، `expiresAt`، `lastUsedAt`، `revokedAt`.

## محدودیت‌ها

| قاعده | مقدار |
| --- | --- |
| حداکثر کلید فعال برای هر کاربر | ۵ (ششمی `409`) |
| انقضا | پیش‌فرض ۹۰ روز، حداکثر ۳۶۵ |
| نرخ درخواست | ۱۲۰ در دقیقه برای هر کلید (`429`)، افزون بر محدودیت IP |
| هشدار | کلید فعالی که ۳۰ روز استفاده نشده در کارت نشان «n روز استفاده نشده» می‌گیرد (از زمان ساخت اگر هرگز) |
| ثبت استفاده | `lastUsedAt`، حداکثر دقیقه‌ای یک بار نوشته می‌شود و نوشتنش هرگز درخواست را خراب نمی‌کند؛ بدنهٔ درخواست‌ها ثبت نمی‌شود |

ساخت و لغو در لاگ ممیزی می‌آید (`api_key.create`، `api_key.revoke`، با نام و پیشوند و دامنه‌ها).

## دسترسی

کلید **هویت صاحبش** را می‌برد با **نقش فعلی** او و فقط از آنچه او می‌بیند و می‌تواند، آن هم کمتر با دامنه:

| دامنه | چه می‌شود |
| --- | --- |
| `contents:read` | `GET /api/v1/topics`، `GET /api/v1/contents`، `GET /api/v1/contents/:id` |
| `contents:write` | `POST /api/v1/topics/:id/contents/generate` (همان درخواست تولید برنامه، با همان سقف پیش‌نویس هم‌زمان؛ AI در ورکر اجرا می‌شود) |
| `calendar:read` | `GET /api/v1/calendar?from&to` |

- حساب فقط‌خواندنی (`VIEWER`) فقط دامنهٔ `:read` می‌گیرد؛ اگر صاحب کلید بعداً تنزل کند، دامنهٔ نوشتن کلیدش همان لحظه کار نمی‌کند.
- **مسیری که `@AllowApiKey(scope)` ندارد برای کلید `403` است** (قبل از هر جست‌وجوی کلید): بازبینی، تأیید، زمان‌بندی، انتشار، ویرایش محتوا، مدیریت خود کلیدها و بقیهٔ API. یک مسیر تازه تصادفاً با کلید باز نمی‌شود. تست قفل می‌کند که فقط پنج مسیر v1 این دامنه را دارند و `ReviewsController`، `CalendarController`، `ContentsController` و `ApiKeysController` هیچ‌کدام ندارند.
- دامنهٔ ناکافی `403`؛ کلید لغوشده/منقضی/کاربر غیرفعال `401`؛ موضوعی که کاربر به آن دسترسی ندارد `404` (همان `@TopicScoped`).

## API v1

پایدار و صریحاً نسخه‌دار: **فقط فیلد اضافه می‌شود، نه تغییر نام و نه حذف.** قرارداد در `packages/shared/src/api-keys.ts` (`ApiV1*`). فهرست‌ها `{ items, total, page, pageSize }` هستند؛ فیلترها فقط `page`، `pageSize`، `topicId`، `status` (محتوا) و `status` (موضوع).

```
curl -H "Authorization: Bearer ctk_…" https://<host>/api/v1/contents?status=APPROVED
curl -X POST -H "Authorization: Bearer ctk_…" -H "Content-Type: application/json" \
     -d '{"brief":"یک پست دربارهٔ قهوهٔ تازه"}' https://<host>/api/v1/topics/<topicId>/contents/generate
```

متن آماده‌شده را با `GET /api/v1/contents/:id` (فیلد `text`) بخوانید.

## ریسک

سطح حمله بالا می‌رود و ثبات v1 تعهد بلندمدت است؛ برای همین فهرست مسیرها کوچک نگه داشته شده، کلیدها کوتاه‌عمرند و تأیید انسانی دست‌نخورده می‌ماند. نرخ‌محدودیت هر کلید در حافظهٔ یک پردازش است (با چند نمونهٔ API هرکدام جدا می‌شمارد).
