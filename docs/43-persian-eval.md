# مجموعه‌تست ارزیابی فارسی (Eval) برای پرامپت‌ها

> وضعیت: **چارچوب و مجموعهٔ تست ساخته شده (نسخهٔ ۰٫۲۰٫۰)؛ هنوز با مدل واقعی اجرا نشده.** بنابراین `eval-baseline.json` خالی است و هیچ عددی دربارهٔ کیفیت مدل ادعا نمی‌شود. نخستین اجرا باید با کلید واقعی انجام شود (بخش ۵).

## ۱. هدف

بدون این مجموعه، عوض‌کردن مدل یا ویرایش پرامپت از بک‌آفیس «کور» است. حالا هر تغییر را می‌شود روی ۹۰ مورد ثابت سنجید و با اجرای قبلی مقایسه کرد.

## ۲. اجزا (`apps/api/src/evals/`)

| فایل | کار |
|---|---|
| `fixtures.ts` | شش برند **ساختگی** (کیف پول، کلینیک پوست، کافه، آموزش آنلاین، مشاور مالیاتی، کتاب‌فروشی) با بخش‌های پروفایل، واقعیت‌های کلیدی، واژه‌نامه، اصول، پروفایل سبک و یک پیش‌نویس منبع |
| `cases.ts` | ساخت موردها؛ متغیرهای پرامپت با همان توابع `format*` که runnerها به کار می‌برند ساخته می‌شود، پس پرامپت واقعی آزموده می‌شود، نه نسخهٔ کپی |
| `checks.ts` | بررسی‌های **قطعی با کد** (بخش ۳) |
| `judge.ts` | داور مدلی، تنظیم‌سنجی (calibration) و قاعدهٔ «داور از خانوادهٔ دیگر» |
| `run-eval.ts` | اجرا و گزارش؛ ارائه‌دهنده را آرگومان می‌گیرد (در تست جعلی، در CLI واقعی) |
| `baseline.ts` | مقایسه با آخرین اجرا و نگهبان تغییر پرامپت |
| `cli.ts` | `npm run eval -w @contenter/api -- ...` |

### موردها (۹۰ مورد)

- **`generate_content` — ۴۲ مورد** = ۶ برند × ۷ سناریو: کپشن اینستاگرام با واقعیت دقیق، اطلاعیهٔ تلگرام با واقعیت دوم، پست لینکدین، رشتهٔ ایکس، کاروسل، و **دو تله**: (الف) بریف مدل را وسوسه می‌کند واژهٔ ممنوع برند را بنویسد؛ (ب) بریف آدرس و کد تخفیفی می‌خواهد که در پروفایل نیست و نباید ساخته شود.
- **`repurpose_content` — ۳۶ مورد** = ۶ برند × ۶ مقصد (تلگرام، لینکدین، رشتهٔ ایکس، بله، ایتا، خبرنامه) از یک کپشن اینستاگرام.
- **`ideate` — ۱۲ مورد** = ۶ برند × دو حالت (۵ ایدهٔ آزاد، ۳ ایدهٔ کاروسل).

## ۳. بررسی‌های قطعی

| بررسی | معنا |
|---|---|
| `persian` | دست‌کم ۶۰٪ حرف‌های عنوان و متن فارسی باشد |
| `quality-gate` | **هیچ هشدار** دروازهٔ کیفیت (docs/41): سقف طول، واژه‌نامه، عدد در برابر واقعیت، جانگهدار، واقعیت منقضی |
| `format-shape` | رشته ≥ ۳ پست؛ کاروسل ≥ ۴ اسلاید شماره‌دار؛ خبرنامه ≥ ۳۰۰ نویسه؛ کپشن بدون عنوان Markdown |
| `cta-present` | دعوت به اقدام خالی نباشد |
| `hashtags-clean` | هشتگ فاصله نداشته باشد |
| `no-invented-numbers` | هر عدد خروجی در پروفایل، بریف یا پیش‌نویس منبع باشد (به‌جز اعداد ≤ ۱۰ و سال‌ها) |
| `quotes-facts` | مقدار دقیق واقعیتی که بریف خواسته بیاید |
| `bait-absent` | (مورد تله) واژهٔ ممنوع نوشته نشود |
| `not-a-copy` | (بازنشر) کمتر از ۸۵٪ واژه‌ها با منبع یکی باشد |
| ایده‌ها | `count-exact`، `distinct-angles`، `outline-3-7`، `honest-scores` (همه یک امتیاز نباشند)، `format-respected`، `brand-terms`، `no-invented-numbers` |

یک مورد فقط وقتی «قبول» است که **همهٔ** بررسی‌هایش (و در صورت وجود داور، داور) قبول باشند.

## ۴. داور مدلی

فقط آنچه کد نمی‌بیند: روانی، طبیعی‌بودن (ترجمه‌ای نبودن)، تطابق با لحن برند، وفاداری به پروفایل و مناسب‌بودن برای پلتفرم، هرکدام ۱ تا ۵. قبول: هیچ بُعدی زیر ۳ و میانگین ≥ ۳٫۵.

دو محافظ:

1. **داور باید از خانوادهٔ دیگری باشد** (`assertDifferentFamily`): نویسنده OpenAI ← داور Anthropic (یا برعکس)، وگرنه اجرا خطا می‌دهد، مگر با `--allow-same-family` و نتیجهٔ جانب‌دارانه.
2. **تنظیم‌سنجی:** پیش از اجرا داور باید روی **۶ جفت متن دست‌ساز** (خوب و بد برای یک بریف: ترجمه‌نما، قیمت ساختگی، ادعای ممنوع، تضمین پزشکی، وعدهٔ سود، آمیختن انگلیسی) متن خوب را دست‌کم یک امتیاز بالاتر بدهد، دست‌کم در ۵ جفت. وگرنه گزارش «داور قابل‌اعتماد نیست» می‌شود و نتیجه‌اش baseline نمی‌شود.

## ۵. اجرا

```bash
npm run eval -w @contenter/api -- --list
npm run eval -w @contenter/api -- --model openai:gpt-5.4 --judge anthropic:claude-sonnet-5
npm run eval -w @contenter/api -- --model openai:gpt-5.4 --judge anthropic:claude-sonnet-5 --task ideate --limit 4
npm run eval -w @contenter/api -- --model mock:test --task generate_content --limit 3
```

- کلیدها از محیط یا `apps/api/.env` (`OPENAI_API_KEY`، `ANTHROPIC_API_KEY`). `mock:` بدون کلید و بدون هزینه کل خط لوله را می‌چرخاند (بررسی‌ها روی متن ثابت mock طبیعتاً رد می‌شوند).
- گزینه‌ها: `--task`، `--effort`، `--judge-effort`، `--limit`، `--filter` (زیررشتهٔ شناسه)، `--concurrency` (پیش‌فرض ۳)، `--out`، `--skip-calibration`.
- گزارش کامل JSON در `apps/api/eval-results/` (در git نیست)، خلاصه در ترمینال: نرخ قبولی، نرخ هر بررسی، شکست‌ها، توکن و هزینه (از `pricing.ts`).
- اجرای دستی در GitHub: workflow «Persian eval» (`workflow_dispatch`) با رازهای `OPENAI_API_KEY` و `ANTHROPIC_API_KEY`.
- **هزینه:** یک اجرای کامل حدود ۹۰ فراخوان نویسنده و ۷۸ فراخوان داور (به‌علاوهٔ ۱۲ برای تنظیم‌سنجی) است؛ با `--limit` ارزان‌تر می‌شود.

## ۶. baseline و نگهبان تغییر پرامپت

- `--update-baseline` یک اجرای **کامل، بدون خطا و با داور معتبر** را در `eval-baseline.json` ثبت می‌کند و هش پرامپت را در `evaluated-prompts.json` می‌گذارد. اجرای جزئی (`--limit`/`--filter`) هرگز baseline نمی‌شود.
- هر اجرا با baseline مقایسه می‌شود؛ **افت بیش از ۵ امتیاز درصدی قبولی** یا **۰٫۳ افت میانگین داور** «رگرسیون» است و کد خروج `1` می‌دهد. اگر baseline با مدل دیگری گرفته شده باشد هشدار می‌دهد.
- **نگهبان در CI:** تست واحد `prompt change guard` هش پرامپت‌های `generate_content`، `repurpose_content` و `ideate` را با `evaluated-prompts.json` می‌سنجد. اگر در `prompts/defaults.ts` یکی را ویرایش کنید، CI قرمز می‌شود تا eval را اجرا و `--update-baseline` را بزنید. کلید مدل در CI لازم نیست، چون قید این است که **کسی eval را اجرا کرده**، نه اینکه CI خودش مدل را صدا بزند.
- نسخه‌های ویرایش‌شده از بک‌آفیس (جدول `PromptTemplate`) این نگهبان را فعال نمی‌کنند؛ برای آن‌ها باید پیش از فعال‌سازی دستی eval را اجرا کرد (مقایسهٔ دو نسخه در بک‌آفیس هنوز نیست).

## ۷. محدودیت‌ها و آنچه راستی‌آزمایی نشد

- **با هیچ مدل واقعی اجرا نشده**؛ آستانه‌ها (۶۰٪ فارسی، ۸۵٪ شباهت، ۰٫۷ تفاوت زاویه، ۳٫۵ داور) برآورد من‌اند و باید پس از نخستین اجرا تعدیل شوند. بررسی‌ها ممکن است بیش‌ازحد سخت یا نرم باشند.
- مجموعه **ساختگی** است (۶ برند × سناریو)، نه پیش‌نویس‌های واقعی. مالک دربارهٔ استفاده از پیش‌نویس‌های تأییدشده به‌عنوان مجموعهٔ طلایی نظری نداشت (۱۳ اکتبر)، پس چنین کاری نشده. ۴۲ مورد تولید از «۳۰ تا ۵۰ مورد» docs/27 است؛ برای بازنشر و ایده کمتر است.
- ۶ جفت تنظیم‌سنجی کم است و فقط تشخیص خطاهای درشت را می‌سنجد؛ داور ممکن است خطای ظریف را از دست بدهد.
- داور برای ایده‌ها اجرا نمی‌شود (فقط بررسی‌های کد).
- تنها پرامپت‌های پیش‌فرض آزموده می‌شوند، نه نسخهٔ فعال در پایگاه‌داده.
- تشخیص «عدد ساختگی» ممکن است عددی را که از واقعیت محاسبه شده (مثلاً مجموع) خطا بگیرد.
