# سلسله‌مراتب محصول، بازار و پرسونا (docs/73)

> **وضعیت: فاز ۱ (A، B، C، H) و فاز ۲ (D، I، J، K) ساخته شد؛ فاز ۳ و ۴ ساخته نشده.** تفاوت‌های ساخت با طرح در بخش ۱۰ و ۱۱. پایه: [67-business-catalog.md](67-business-catalog.md) (کاتالوگ تخت). ربطی به زیربرند ([71](71-business-sub-brands.md)) ندارد: اینجا **یک برند** است با چند محصول؛ زیربرند یعنی چند برند.

## ۱. مسئله

یک برند چند محصول/خدمت دارد و هر کدام ویژگی، بازار و مخاطب خودش را. مثال ویپاد: «تسهیلات با سرمایه‌گذاری» یک خط محصول است؛ زیرش انواع تسهیلات (مثلاً برای کسب‌وکار کوچک، برای خرید تجهیزات، برای افراد حقوق‌بگیر…) هر کدام شرایط، بازار و پرسونای متفاوت دارند و پیام «قانع‌کننده» برایشان فرق می‌کند.

### وضع فعلی (از خواندن کد)
- `BusinessOffering` **تخت** است: نه والد/فرزند دارد، نه بازار، نه پرسونا. تنها پیوندها `complementIds` / `substituteIds` (مکمل/جایگزین) هستند.
- بازار و پرسونا فقط **دو بخش متنی** کل برندند (`TARGET_MARKET`، `PERSONAS`، docs/12). متن «۲–۴ پرسونا» برای کل برند است و نمی‌گوید کدام پرسونا مال کدام محصول است.
- `Topic` (پروژه) فقط `businessId` دارد؛ **هیچ پیوندی به محصول نیست**. پس وقتی ادمین برای «تسهیلات تجهیزات» پروژه می‌سازد، مدل کل کاتالوگ و همهٔ پرسوناها را می‌بیند و باید حدس بزند.
- پیوند محتوا↔محصول (docs/67 §4.8) هنوز ساخته نشده.

نتیجه: پیام‌ها یکدست و کلی می‌شوند، یا مدل مشخصات یک محصول را به محصول دیگر می‌چسباند (خطر انطباق: شرایط وام اشتباه!).

## ۲. اصل طراحی

1. **محصول را درخت کن، نه فهرست تخت** (حداکثر ۳ سطح: خط محصول ← محصول ← گونه/پلن).
2. **مخاطب و بازار را موجودیت ساختاریافته کن** (`BusinessSegment`) و آن را به محصول‌ها وصل کن؛ نه متن آزاد.
3. **پروژه/محتوا یک «تمرکز» داشته باشد**: وقتی کانون یک محصول است، پرامپت فقط همان محصول + اجداد + بخش‌های مخاطب مرتبطش را با جزئیات می‌گیرد و بقیه کاتالوگ فقط یک خط.
4. **وراثت با قاعدهٔ روشن:** فرزند ویژگی/مدرک/ممنوعیت‌های والد را «می‌خواند» (در لحظهٔ ساخت پرامپت، با کد) ولی ذخیره نمی‌کند؛ هر چیز را فرزند بنویسد، بر والد ارجحیت دارد. این وراثتِ *محتوای محصول* است، نه وراثت برند (که docs/71 آن را رد کرد).
5. **AI پیشنهاد می‌دهد، کد می‌سنجد:** همان الگوی `resolveOfferingProposals` (نقل‌قول واقعاً در منبع باشد؛ تأییدنشده به مدل نمی‌رود).
6. **بدون تغییر قالب پرامپت‌های eval-guard:** همه داخل متغیر `business` می‌رود؛ بدون سلسله‌مراتب، بایت‌ها عیناً مثل قبل.

## ۳. مدل داده (پیشنهادی)

```prisma
model BusinessOffering {
  // ... فیلدهای فعلی
  parentId   String?          // خط محصول؛ عمق ≤ ۳؛ onDelete: SetNull یا Restrict (بخش ۸)
  parent     BusinessOffering? @relation("OfferingTree", ...)
  children   BusinessOffering[] @relation("OfferingTree")
  /// شروط/محدودیت‌ها و ادعاهای ممنوع (مثلاً «سود تضمینی نگو»)
  guardrails String[]
  segmentLinks OfferingSegment[]
}

enum SegmentKind { MARKET PERSONA }

model BusinessSegment {
  id          String @id @default(cuid())
  businessId  String
  kind        SegmentKind          // MARKET (بازار/بخش) | PERSONA (آدم)
  name        String
  summary     String   // ≤ ۴۰۰
  // بازار: جغرافیا، B2B/B2C، اندازه؛ پرسونا: سن/شغل/هدف/درد/اعتراض/کانال
  attributes  Json     // { goals, pains, objections, channels, triggers, … } با Zod
  messageAngle String  // «چه پیامی قانع‌شان می‌کند»
  tone        String?  // اختیاری: نمایش لحن ویژه، نه نادیده‌گرفتن راهنمای برند
  source      SectionSource @default(ADMIN)
  verified    Boolean @default(true)
  isActive    Boolean @default(true)
  evidence    String  @default("")
  // @@unique([businessId, name])
}

model OfferingSegment {          // N:M با «نقش»
  offeringId String
  segmentId  String
  fit        Int  // 1 = فرعی · 2 = اصلی
  note       String @default("")
  // @@id([offeringId, segmentId])
}

// Topic و Content / Idea:
//   Topic.offeringId?, Topic.segmentId?   تمرکز پروژه
//   Content.offeringId?, Content.segmentId?  تمرکز یک محتوا (پیش‌فرض از پروژه)
```
قاعدهٔ مالکیت مثل `pillarId`/`styleId`: باید متعلق به **کسب‌وکار همان پروژه** باشد (سرویس چک می‌کند، تغییر کسب‌وکار آن را پاک می‌کند). برچسب را آدم می‌زند، مدل نه.

حدها (ثابت نام‌دار در shared): ≤ ۶۰ محصول (همان فعلی)، ≤ ۴۰ بخش، ≤ ۸ بخش مخاطب به ازای هر محصول.

## ۴. پرامپت

داخل همان `business` (بخشی از `buildBusinessParts`؛ پس پیش‌نمایش docs/66 خودکار آن را نشان می‌دهد):
- `[CATALOG]` فعلی: وقتی درخت وجود دارد، به‌صورت تو‌رفته (والد ← فرزند). 
- **وقتی تمرکز تنظیم است** (`[FOCUS]`): زنجیرهٔ محصول (جد ← خودش) با ویژگی/مدرک/ممنوعیت‌ها کامل؛ محصول‌های هم‌ردیف فقط نام و یک خط (برای مقایسه‌نکردن اشتباه)؛ بخش‌های مخاطب پیوندخورده با `attributes` و `messageAngle`؛ سپس بخش‌های `TARGET_MARKET`/`PERSONAS` برند **کوتاه‌شده** (خلاصه) تا بودجهٔ ۳۰٬۰۰۰ نویسه نخورد.
- **بدون تمرکز:** رفتار فعلی؛ فقط کاتالوگ درختی.
- قاعدهٔ تقدم یک خط (مثل `[STYLE]`): «اگر [FOCUS] هست، ویژگی و شرایط را فقط از همان بگیر؛ هرگز مشخصات یک محصول را به دیگری نسبت نده».

## ۵. دروازهٔ کیفیت (کد، فقط هشدار)
- `OFFERING_CROSSED`: متن نام محصول **هم‌ردیف** را دارد و عدد/شرط قیمتی یا ویژگی **انحصاری** آن را (از `features`/`claims`) می‌آورد ولی محصول تمرکز آن را ندارد.
- `GUARDRAIL_HIT`: عبارت ممنوع ثبت‌شده در `guardrails` در متن آمد (با `fold`، نه مدل).
- همان قاعدهٔ docs/67: `warn`، هرگز بازبینی/انتشار را نمی‌بندد.

## ۸. ریسک‌ها و سؤال‌های باز
- **حذف والد:** پیشنهاد `Restrict` (باید ابتدا فرزندها جابه‌جا یا حذف شوند) تا پیوندها و محتواها یتیم نشوند؛ جایگزین: `SetNull` و تبدیل فرزند به ریشه. سؤال مالک.
- **انفجار پرامپت:** با ۶۰ محصول و ۴۰ مخاطب باید `[FOCUS]` بودجه‌بندی شود؛ بدون تمرکز فقط نام‌ها و یک خط. پیش از اضافه‌کردن سقف جدید، با پیش‌نمایش docs/66 اندازه‌گیری شود.
- **اختلاط با بخش‌های متنی `PERSONAS`/`TARGET_MARKET`:** متن می‌ماند (روایت)؛ مخاطب ساختاریافته منبع واقعیت برای پرامپت تمرکزدار است. تناقض‌یابی با کد در فاز بعد.
- **قفل بخش (docs/69):** `BusinessSegment` متن آزاد بخش نیست؛ قفل ندارد. اگر `messageAngle` را AI بنویسد، بازبینی‌نشده می‌ماند تا ادمین تأیید کند.
- **سؤال‌ها برای مالک:**
  ۱. در ویپاد واقعاً چند خط محصول و چند گونه داریم؟ (سه سطح کافی است یا دو سطح؟)
  ۲. پرسونا برای هر محصول جدا نوشته می‌شود یا چند پرسونای مشترک بین محصول‌ها؟ (طرح N:M فرض می‌کند مشترک)
  ۳. آیا گزاره‌های ممنوع/الزام قانونی (بانکی) را باید جدی بگیریم و در `guardrails` بنویسیم؟
  ۴. حذف والد: `Restrict` یا `SetNull`؟

## ۱۰. فاز ۱: آنچه ساخته شد و تفاوت با طرح

**پیش‌فرض‌های سؤال‌های بخش ۸ (تا پاسخ مالک):** سه سطح (`OFFERING_TREE_DEPTH_MAX`)، مخاطب مشترک بین محصول‌ها (N:M)، حذف والد دارای فرزند ← ۴۰۰ «ابتدا زیرمجموعه‌ها را جابه‌جا یا حذف کنید».

**کد:**
- shared: `offering-tree.ts` (`offeringParentProblem`، `orderOfferingTree`، `hasOfferingTree`، `effectiveGuardrails`، `offeringQualityRules`)، `business-segments.ts` (اسکیماها، `OfferingSegmentLink`)، فیلدهای `parentId` / `guardrails` در `business-catalog.ts`، کد تازهٔ `GUARDRAIL_HIT` در انتهای `QualityIssueCode`.
- API: migration `20261027100000_offering_hierarchy` (`BusinessOffering.parentId` با `ON DELETE NO ACTION`، `guardrails`، جدول‌های `BusinessSegment` و `OfferingSegment`)، `SegmentsService`/`SegmentsController` (`/businesses/:id/segments`، `/business-segments/:id`)، `PUT /business-offerings/:id/segments`، بررسی درخت در `OfferingsService.assertParent`.
- رابط: برگهٔ «مخاطب‌ها»، نمایش درختی در «محصولات و خدمات» با دکمهٔ «افزودن زیرمجموعه»، فیلدهای والد، عبارت‌های ممنوع و مخاطب‌ها در فرم.

**تفاوت‌ها با طرح:**
- `parentId` با **`NoAction`** است نه `Restrict`: `Restrict` فوری سنجیده می‌شود و حذف کل کسب‌وکار (cascade) را از میان خط و گونه‌هایش می‌شکست. حفاظت اصلی در سرویس است (۴۰۰) و پایگاه داده پشتیبان.
- `BusinessSegment` در فاز ۱ فقط `isActive` دارد؛ `source` / `verified` / `evidence` همراه فاز ۴ (AI) می‌آیند. ویژگی‌های مخاطب ستون‌های `String[]` هستند (`goals`، `pains`، `objections`، `channels`) نه JSON.
- **مخاطب‌ها هنوز به هیچ پرامپت، خروجی Docoo/Researcher یا بررسی نمی‌رسند** (فاز ۲ برای `[FOCUS]`، فاز ۳ برای خروجی).
- `[CATALOG]`: وقتی درخت هست، گونه‌ها زیر خط خود و تورفته می‌آیند با «Part of: …» و یک جملهٔ راهنما در سرآغاز؛ «Never say: …» عبارت‌های خود مورد و والدهایش (یک‌بار هر کدام) را می‌آورد. بدون درخت و بدون عبارت ممنوع، بایت‌ها عیناً همان قبل است (تست). والد غیرفعال/تأییدنشده در پرامپت وجود ندارد، پس گونه‌اش ریشه دیده می‌شود (بدون «Part of»)، ولی **عبارت‌های ممنوعِ** والد و جدِ آن همچنان اعمال می‌شود: ردیف از طریق رابطهٔ `parent` (دو سطح) آن‌ها را می‌خواند، چه والد روشن باشد چه خاموش (در `[CATALOG]` و `GUARDRAIL_HIT` هر دو). وضعیت «متوقف» خط، گونه‌ها را پنهان نمی‌کند.
- `GUARDRAIL_HIT` (`warn`): اگر متن **در جایی** نام مورد (یا نام‌های دیگرش) را بیاورد، کل متن برای عبارت‌های ممنوع آن مورد و والدهایش بررسی می‌شود (نه فقط همان جمله، تا وعدهٔ جملهٔ بعد جا نیفتد). خط با عبارت‌های ممنوع گونه‌اش بسته نمی‌شود. به `STALE_CODES` اضافه نشد.
- `OFFERING_CROSSED` (ایدهٔ J) در فاز ۲ می‌ماند.

**تست‌ها:** `offering-tree.spec.ts` (shared)، `offering-hierarchy.spec.ts` (API)، `offerings.test.tsx` (رابط). راستی‌آزمایی: migration روی PGlite تازه اعمال شد و `prisma migrate diff` بدون اختلاف است.

## ۱۱. فاز ۲: تمرکز پروژه و محتوا؛ آنچه ساخته شد و تفاوت با طرح

**کد:**
- shared: `business-focus.ts` (`FocusFieldsSchema`، `effectiveFocus`، `focusAllowedIds`، `FocusForPrompt`، `MAX_FOCUS_TEXT`)، کد تازهٔ `OFFERING_CROSSED` در انتهای `QualityIssueCode`، ورودی `focus` در `checkContentQuality`، و `id` / `features` در `QualityOfferingRule`.
- پایگاه داده: migration `20261028100000_offering_focus` (`Topic.offeringId/segmentId`، `Content.offeringId/segmentId`، همه با `ON DELETE SET NULL`).
- API: `BusinessApi.focusForPrompt` (تنها خواننده برای پرامپت)، `hasOffering` / `hasSegment`؛ `TopicsService.assertFocus` و `ContentsService.update` (۴۰۰ برای مورد یا مخاطبِ کسب‌وکار دیگر)؛ `ContextLoader.business(..., { focus })`؛ بلوک `FOCUS` در `buildBusinessParts` (بعد از `CATALOG`، پیش از `TERMS`).
- رابط: انتخاب محصول و مخاطب در فرم پروژه، «محصول/مخاطبِ این نوشته» در کارت «سازمان‌دهی» محتوا، یادداشت «برای: … / پیام قانع‌کننده: …» در دیالوگ ساخت پیش‌نویس، و پرکردن «جهت» در ایده‌پردازی.

**قاعده‌ها:**
- **تمرکز مؤثر** = تمرکز خود محتوا، و هرچه خالی باشد از پروژه (`effectiveFocus`). `null` روی محتوا یعنی «همان پروژه».
- **کدام کارها `[FOCUS]` می‌گیرند:** ایده‌پردازی (تمرکز پروژه)، نوشتن پیش‌نویس، بازبینی و بازنشر (تمرکز محتوا) و پیش‌نمایش docs/66 برای هدف «پیش‌نویس» و «ایده‌پردازی». ساخت پروفایل و یادگیری از ویرایش‌ها نمی‌گیرند (بایت‌هایشان همان قبل است).
- **بدون تمرکز، بایت‌ها عیناً همان قبل است** (تست). قالب هیچ پرامپتی ویرایش نشد (نگهبان eval)؛ همه داخل متغیر `business` است.
- `[FOCUS]` فقط ردیف‌های **فعال و تأییدشده** و مخاطب‌های **فعال** را می‌آورد. محصولِ انتخاب‌شده اگر خاموش شود، بلوک فقط مخاطب را نشان می‌دهد (یا هیچ). زنجیرهٔ خط‌ها فقط تا والدهای روشن می‌رود؛ عبارت‌های ممنوع والد خاموش همچنان از طریق `parent` اعمال می‌شود (فاز ۱).
- مخاطب: اگر انتخاب شده باشد همان (کامل)، وگرنه تا ۳ مخاطب پیوندخوردهٔ محصول، اصلی‌ها اول (`FOCUS_SEGMENTS_MAX`). همسایه‌ها = محصول‌های روشنِ زیر همان خط (یا سایر خط‌ها برای یک خط)، فقط نام، تا ۸ مورد.
- `[FOCUS]` بودجه ۴٬۰۰۰ نویسه دارد (`MAX_FOCUS_TEXT`) و مثل بقیه با `budgeted` بریده می‌شود؛ در پیش‌نمایش docs/66 بلوک جدا و قابل‌دیدن است.
- **`OFFERING_CROSSED`** (`warn`): محتوا دربارهٔ محصول F است و جمله‌ای که نام محصول دیگر X را می‌آورد، یا قیمتِ X را می‌گوید (که با قیمت F یکی نیست) یا یکی از ویژگی‌های X را (که F ندارد، دست‌کم ۴ نویسه، عبارت کامل). مجاز: خود F، خط‌های بالا، گونه‌های پایین، و مکمل/جایگزین‌هایی که ادمین نام برده (`focusAllowedIds`). محصولِ متوقف‌شده بررسی نمی‌شود. به `STALE_CODES` اضافه نشد و فقط نمایشی است.

**تفاوت‌ها با طرح:**
- `Idea.offeringId` ساخته **نشد**: ایده از پروژه می‌آید و پیش‌نویسِ ایده تمرکز پروژه را می‌گیرد؛ هر محتوا هم می‌تواند خودش عوض کند. اگر بعداً لازم شد، افزودنش افزایشی است.
- بخش‌های `TARGET_MARKET` / `PERSONAS` پروفایل **کوتاه نمی‌شوند** (طرح §4 این را پیشنهاد کرده بود). بدون اندازه‌گیری حجم واقعی، کوتاه‌کردن خودکار ریسک دارد (قاعدهٔ docs/66: نسخهٔ ۱ فقط نشان می‌دهد و هشدار می‌دهد).
- ایدهٔ I (زاویهٔ پیام) به‌صورت یادداشت در دیالوگ ساخت پیش‌نویس است؛ خود `messageAngle` به مدل از طریق `[FOCUS]` می‌رسد.
- ایدهٔ K فقط فیلد «جهت» را پر می‌کند (`ideas.focusDirection`)؛ قالب پرامپت `ideate` ویرایش نشد.
