# گردش بازبینی و تأیید محتوا

محتوا پیش از تأیید از یک مسیر مشخص می‌گذرد: **نویسنده ← ویراستار ← تأییدکننده**. هر مرحله یک ثبت در تاریخچه دارد و روی پیش‌نویس می‌شود **کامنت** گذاشت. این بخش **بدون AI** است و قاعده‌هایش با کد اجرا می‌شود.

## نقش‌ها

| نقش در گردش | چه کسی | چه کاری می‌تواند |
|---|---|---|
| **نویسنده** | هر کس به موضوع دسترسی «ویرایش» دارد ([17-project-access.md](17-project-access.md)) | ارسال برای بازبینی، پس گرفتن، بازگرداندن به پیش‌نویس |
| **ویراستار** | نقش `EDITOR` یا `ADMIN` | تأیید مرحلهٔ ویراستاری، درخواست اصلاح، رد |
| **تأییدکننده** | فقط `ADMIN` | تأیید نهایی، درخواست اصلاح، رد |

قاعده‌ها:
- ویراستار **بازبینیِ محتوایی را که خودش فرستاده نمی‌تواند** تأیید کند (مدیر می‌تواند).
- مدیر می‌تواند با **«تأیید نهایی مستقیم»** (`finalize`) از پیش‌نویس یا مرحلهٔ ویراستاری مستقیم به «تأییدشده» برود.
- نویسنده (یا مدیر) تا وقتی محتوا در بازبینی است می‌تواند آن را **پس بگیرد**.
- «درخواست اصلاح» و «رد» **یادداشت اجباری** دارند (حداقل ۳ نویسه)؛ همان یادداشت در تاریخچه می‌ماند.

## وضعیت‌ها

```
پیش‌نویس ──ارسال──▶ در بازبینی (ویراستاری) ──تأیید ویراستار──▶ در بازبینی (تأیید نهایی) ──تأیید مدیر──▶ تأییدشده
   ▲                        │  ▲                                       │
   └── درخواست اصلاح / پس گرفتن ┘  └───────── درخواست اصلاح ────────────┘
رد ← ردشده ──بازگشت──▶ پیش‌نویس      تأییدشده ──بازگشت──▶ پیش‌نویس
```

- `Content.status` همان وضعیت‌های قبلی است؛ `Content.reviewStage` (`EDITORIAL` یا `FINAL`) فقط وقتی `IN_REVIEW` است مقدار دارد.
- **تنظیم «تأیید نهایی لازم است»** (بک‌آفیس ← تنظیمات ← «گردش تأیید محتوا»، کلید `workflow` در `SystemSetting`): اگر خاموش باشد، تأیید ویراستار (یا مدیر) همان‌جا محتوا را «تأییدشده» می‌کند؛ مناسب تیم‌های بدون مدیرِ فعال. پیش‌فرض: روشن.
- **ویرایش متن، بازگردانی نسخهٔ دیگر و بازنویسی با AI، محتوای در بازبینی یا تأییدشده را به پیش‌نویس برمی‌گردانند** و در تاریخچه ثبت `RESET` می‌شود؛ چون متنِ بازبینی‌شده عوض شده است. بازگردانی نسخه‌ای که همین حالا فعلی است چیزی را عوض نمی‌کند.

## یک منبع حقیقت: `packages/shared/src/workflow.ts`

`reviewActionsFor(subject, actor, settings)` می‌گوید یک کاربر الان چه کاری می‌تواند بکند و `applyReviewAction` وضعیت بعدی یا دلیل رد را برمی‌گرداند. API با همین توابع تصمیم می‌گیرد و جزئیات محتوا (`GET /contents/:id`) فیلد `review.actions` را برای کاربر جاری برمی‌گرداند؛ وب فقط همان دکمه‌ها را نشان می‌دهد. پس منطق نقش‌ها در کلاینت تکرار نشده است.

- کار ممنوع در وضعیت فعلی ← **۴۰۹**؛ کار مجاز برای کسی با نقش بالاتر ولی نه این کاربر ← **۴۰۳**.
- تغییر وضعیت با مقایسه‌وتنظیم انجام می‌شود (`updateMany` با شرط وضعیت و مرحلهٔ قبلی)؛ اگر دو نفر هم‌زمان تصمیم بگیرند، فقط یکی موفق می‌شود و دیگری ۴۰۹ می‌گیرد.

## تاریخچه (`ContentReview`)

هر قدم یک ردیف دارد: `decision` (`SUBMITTED`، `APPROVED`، `CHANGES_REQUESTED`، `REJECTED`، `WITHDRAWN`، `REOPENED`، `RESET`)، `stage`، `actorId`، `versionId` (نسخه‌ای که دربارهٔ آن تصمیم گرفته شد) و `note`. جزئیات محتوا ۵۰ ردیف آخر را (تازه‌ترین اول) در `reviews` دارد. حذف کاربر، نام او را از تاریخچه خالی می‌کند ولی ردیف می‌ماند.

## کامنت (`ContentComment`)

- هر نظر به **نسخه‌ای که نویسنده‌اش آن را می‌دید** وصل است (پیش‌فرض: نسخهٔ فعلی) و در رابط با شمارهٔ نسخه دیده می‌شود؛ نظر دربارهٔ نسخهٔ قدیمی با نشان خاکستری می‌آید.
- رشته‌ها یک سطح پاسخ دارند؛ پاسخ به پاسخ ← ۴۰۰. پاسخ همیشه روی نسخهٔ رشته‌اش می‌ماند.
- «حل شد» فقط برای نظر اصلی است؛ هر کس به موضوع دسترسی ویرایش دارد می‌تواند حل کند یا دوباره باز کند.
- فقط **نویسندهٔ نظر** آن را ویرایش می‌کند؛ نویسنده یا مدیر می‌تواند حذف کند و پاسخ‌ها با نظر اصلی حذف می‌شوند.
- نوشتن کامنت دسترسی «ویرایش» می‌خواهد؛ «فقط مشاهده» می‌تواند بخواند.

## API

| متد | مسیر | توضیح |
|---|---|---|
| POST | `/contents/:id/review/:action` | `action` یکی از `submit`، `approve`، `finalize`، `request_changes`، `reject`، `withdraw`، `reopen`؛ بدنه `{ note? }` ← `{ status, reviewStage }` |
| GET | `/contents/:id` | علاوه بر قبل: `review { actions, requireFinalApproval }`، `reviews[]`، `submittedBy`، `reviewStage` |
| PATCH | `/contents/:id` | **دیگر `status` را قبول نمی‌کند** (۴۰۰)؛ فقط `title` و `campaignId` |
| GET / POST | `/contents/:id/comments` | رشته‌ها با پاسخ‌ها / `{ body, versionId?, parentId? }` |
| PATCH / DELETE | `/comments/:id` | `{ body?, resolved? }` / حذف |
| GET / PUT | `/admin/settings/workflow` | فقط ADMIN؛ `{ requireFinalApproval }` |

لاگ ممیزی: `content.review.<action>`، `content.comment`، `content.comment_reply`، `content.comment_edit`، `content.comment_resolve`، `content.comment_delete` و `settings.update` برای کلید `workflow`.
