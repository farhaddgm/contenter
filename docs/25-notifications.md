# اعلان‌ها

وقتی چیزی برای محتوای یک نفر رخ می‌دهد (بازبینی، نظر، رسیدن زمان انتشار) به او خبر داده می‌شود. این بخش **بدون AI** است: گیرنده‌ها از نقش و دسترسی می‌آیند و متن از قالب. سه کانال دارد:

| کانال | برای که | تنظیم |
|---|---|---|
| **درون‌برنامه‌ای** (زنگ بالای صفحه و صفحهٔ «اعلان‌ها») | هر کاربر، همیشه | هر کاربر برای هر رویداد روشن/خاموش می‌کند |
| **ایمیل** | هر کاربر | نیاز به `SMTP_URL` در env سرور؛ هر کاربر برای هر رویداد روشن/خاموش می‌کند |
| **وب‌هوک** (یک نشانی برای کل سیستم) | سیستم‌های بیرونی (Slack/n8n/…) | ادمین در بک‌آفیس ← تنظیمات |

اعلان هیچ‌وقت کار اصلی را خراب نمی‌کند: اگر ایمیل یا وب‌هوک یا حتی پیدا کردن گیرنده‌ها خطا بدهد، گام بازبینی یا نظر همچنان انجام و ثبت می‌شود.

## رویدادها و گیرنده‌ها

| رویداد | چه وقت | گیرنده‌ها | پیش‌فرض ایمیل |
|---|---|---|---|
| `REVIEW_SUBMITTED` | محتوا برای بازبینی فرستاده شد | ویراستارها و مدیرانی که به موضوع دسترسی «ویرایش» دارند | بله |
| `REVIEW_FINAL_NEEDED` | ویراستار تأیید کرد و محتوا منتظر تأیید نهایی است | مدیران | بله |
| `REVIEW_APPROVED` | تأیید شد (نهایی، یک‌مرحله‌ای یا مستقیم) | سازنده و فرستندهٔ محتوا | بله |
| `REVIEW_CHANGES_REQUESTED` | اصلاح خواستند (با دلیل) | سازنده و فرستنده | بله |
| `REVIEW_REJECTED` | رد شد (با دلیل) | سازنده و فرستنده | بله |
| `COMMENT_ADDED` | نظر تازه (رشتهٔ تازه) | سازنده، فرستنده و نظردهندگان قبلیِ آن محتوا | **خیر** |
| `COMMENT_REPLIED` | پاسخ در یک رشته | سازنده، فرستنده و نظردهندگانِ همان رشته | **خیر** |
| `CONTENT_DUE` | زمان انتشار محتوای تأییدشده رسید ([22-calendar-publishing.md](22-calendar-publishing.md)) | سازنده، فرستنده و آخرین تأییدکننده؛ اگر هیچ‌کدام نبودند مدیران | بله |

- **خودِ کنشگر هیچ‌وقت اعلان نمی‌گیرد** و هر گیرنده یک بار (حتی اگر در چند نقش باشد).
- گیرنده فقط کسی است که **همین حالا به موضوع دسترسی دارد** (دسترسی «مشاهده» برای خبر کافی است، برای بازبینی «ویرایش»)، یعنی همان قاعده‌های [17-project-access.md](17-project-access.md): مدیر همیشه، سازندهٔ موضوع، و عضوهای دارای دسترسی؛ کاربر غیرفعال هرگز. نقش `VIEWER` با دسترسی «ویرایش» می‌تواند بنویسد ولی «بازبین» حساب نمی‌شود.
- پیش‌فرض‌ها (`NOTIFICATION_DEFAULTS`): همه‌چیز درون‌برنامه‌ای؛ ایمیل فقط برای تصمیم‌ها و یادآور، نه نظرها (پرتعداد).

### یادآور زمان انتشار

`ContentReminderService` هر ۵ دقیقه (در همان پروسه‌ای که worker است؛ `APP_ROLE` برابر `worker` یا `all`، نه `api`) محتوای `APPROVED` منتشرنشده‌ای را که `scheduledAt` رسیده است (تا ۱۴ روز قبل) پیدا می‌کند و `CONTENT_DUE` می‌فرستد.

- **یک بار برای هر برنامه:** `Content.dueNotifiedFor` همان `scheduledAt` را نگه می‌دارد؛ جابه‌جا کردن برنامه دوباره آماده‌اش می‌کند. پیش از فرستادن، ردیف با `updateMany` شرطی «گرفته» می‌شود تا اگر دو worker هم‌زمان بودند فقط یکی بفرستد.
- در همین چرخه، اعلان‌های **خوانده‌شده**ٔ قدیمی‌تر از ۶۰ روز و لاگ ارسال‌ها (ایمیل/وب‌هوک) قدیمی‌تر از ۳۰ روز پاک می‌شوند.

## متن اعلان

متن در پایگاه داده **ذخیره نمی‌شود**؛ فقط `params` (`contentTitle`، `actorName`، `note`، `when`) و `event` ذخیره می‌شود و متن را `notificationMessage()` در `packages/shared/src/notifications.ts` به زبان خواننده می‌سازد. وب و ایمیل و وب‌هوک از همین یک تابع استفاده می‌کنند، پس یک جمله می‌گویند. ایمیل و وب‌هوک فارسی‌اند. `note` (دلیل تصمیم یا متن نظر) تا ۲۸۰ نویسه کوتاه می‌شود. زمان `CONTENT_DUE` با تقویم شمسی و زمان تهران نوشته می‌شود.

## ایمیل

- `SMTP_URL` (مثلاً `smtps://user:pass@smtp.example.com:465`) و `MAIL_FROM` در `apps/api/.env`. خالی = ایمیل خاموش (کاربر در «حساب من» هم می‌بیند که ایمیل در دسترس نیست). نیاز به `APP_URL` درست دارد چون پیوند محتوا از آن ساخته می‌شود.
- موضوع ایمیل همان عنوان اعلان است؛ متن: دلیل/نظر و پیوند محتوا.
- هر ارسال تا ۳ بار تلاش می‌شود (فاصله‌ها ۱ و ۵ ثانیه، در حافظهٔ همان پروسه؛ با ری‌استارت وسط تلاش از دست می‌رود) و نتیجه در `NotificationDelivery` ثبت می‌شود. بدون صف پایدار عمداً: اعلان بهترین‌تلاش است، نه تضمینی.

## وب‌هوک

بک‌آفیس ← تنظیمات ← «ایمیل و وب‌هوک اعلان‌ها»: نشانی (http/https)، رمز امضا (اختیاری، دست‌کم ۱۶ نویسه) و رویدادهایی که فرستاده شوند. برای هر رویداد انتخاب‌شده **یک** درخواست `POST` با JSON (نه یکی برای هر گیرنده):

```json
{
  "id": "uuid", "event": "REVIEW_APPROVED", "occurredAt": "2026-10-10T09:00:00.000Z",
  "title": "سارا محتوای «…» را تأیید کرد", "body": "",
  "actor": { "id": "…", "name": "سارا" },
  "content": { "id": "…", "title": "…", "topicId": "…" },
  "url": "https://…/app/contents/…", "recipientCount": 2
}
```

هدرها: `X-Contenter-Event` (نام رویداد؛ `test` برای دکمهٔ «ارسال آزمایشی»)، `X-Contenter-Delivery` (همان `id`)، `X-Contenter-Timestamp` (ثانیهٔ یونیکس) و، با رمز، `X-Contenter-Signature: sha256=<hex>` که HMAC-SHA256 رشتهٔ `"<timestamp>.<body>"` است. گیرنده باید امضا را با رمز بازحساب کند و `timestamp` را هم بسنجد (مثلاً بیش از ۵ دقیقه کهنه نباشد) تا درخواست ضبط‌شده دوباره پخش نشود.

- پاسخ 2xx = موفق؛ هر چیز دیگر (از جمله ریدایرکت، که دنبال نمی‌شود) یا مهلت ۵ ثانیه = ناموفق و تا ۳ بار تلاش.
- رمز با `SecretBox` رمز می‌شود (کلید از `DATA_ENCRYPTION_KEY`، وگرنه `JWT_REFRESH_SECRET`) و هرگز برنمی‌گردد؛ API فقط می‌گوید «رمز ذخیره شده». کلید مقدار نامعتبر یا عوض‌شده = وب‌هوک بدون امضا.
- در لاگ ارسال فقط **میزبان** نشانی ذخیره می‌شود (مسیر ممکن است توکن داشته باشد). نشانی را فقط ادمین می‌گذارد؛ نشانی شبکهٔ داخلی هم مجاز است (برای n8n و مانند آن).

## مدل داده

migration `20261011090000_notifications`: `Notification` (کاربر، رویداد، `params`، پیوند، `readAt`)، `NotificationPreference` (یکتا برای هر کاربر و رویداد؛ نبودنش یعنی پیش‌فرض)، `NotificationDelivery` (ایمیل/وب‌هوک، موفق یا ناموفق، خطا، تعداد تلاش) و ستون `Content.dueNotifiedFor`. حذف کاربر یا محتوا اعلان‌هایش را هم پاک می‌کند.

## API

همهٔ نقش‌ها (حتی `VIEWER`) اعلان‌ها و ترجیحات **خودشان** را می‌خوانند و عوض می‌کنند.

| متد | مسیر | توضیح |
|---|---|---|
| GET | `/notifications?unread&page&pageSize` | اعلان‌های من، تازه‌ترین اول |
| GET | `/notifications/unread-count` | `{ count }` (وب هر ۳۰ ثانیه می‌پرسد، وقتی تب پنهان است نه) |
| POST | `/notifications/:id/read` | ۲۰۴؛ اعلان کس دیگر ← ۴۰۴ |
| POST | `/notifications/read-all` | `{ updated }` |
| GET | `/notifications/preferences` | `{ emailAvailable, preferences[] }` برای هر هشت رویداد |
| PUT | `/notifications/preferences/:event` | `{ inApp?, email? }`؛ آنچه نیامده می‌ماند |
| GET / PUT | `/admin/settings/notifications` | فقط ADMIN. `{ webhookUrl, webhookSecret?, webhookEvents }` ← بدون رمز. `webhookSecret` نیامدن = نگه‌داشتن، `null` = حذف؛ خاموش کردن وب‌هوک رمزش را هم پاک می‌کند |
| POST | `/admin/settings/notifications/test` | یک پیام آزمایشی به ایمیل خودِ ادمین و به وب‌هوک؛ نتیجهٔ هر کانال `sent` / `skipped` / `{ error }` |
| GET | `/admin/notification-deliveries` | آخرین ارسال‌های ایمیل و وب‌هوک با وضعیت و خطا |

لاگ ممیزی: `settings.update` برای کلید `notifications` (بدون رمز).

## رابط

- **زنگ** در نوار بالا با شمار خوانده‌نشده، فهرست آخرین ۸ اعلان، «همه را خوانده کن» و پیوند به صفحهٔ **اعلان‌ها** (فیلتر خوانده‌نشده، صفحه‌بندی). کلیک روی اعلان آن را خوانده می‌کند و به محتوا می‌برد.
- **حساب من**: جدول رویداد × (درون‌برنامه‌ای، ایمیل).
- **تنظیمات (ادمین)**: وضعیت ایمیل، وب‌هوک، «ارسال آزمایشی» و آخرین ارسال‌ها.

## تست

- `packages/shared/src/notifications.spec.ts` — متن هر رویداد در دو زبان، کوتاه‌سازی، تقویم شمسی، اسکیماها.
- `apps/api/src/modules/notifications/notifications.spec.ts` — امضا، وب‌هوک، ایمیل، گیرنده‌ها و دسترسی، تلاش دوباره و لاگ، تنظیمات و رمز، صندوق ورودی، یادآور.
- `apps/api/src/modules/reviews/reviews.spec.ts` — چه کسی برای کدام گام بازبینی و نظر خبردار می‌شود، و اینکه خطا در اعلان گام را خراب نمی‌کند.
