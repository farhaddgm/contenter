# پروفایل کسب‌وکار از روی حساب اینستاگرام و سایت

> وضعیت: **پیاده‌سازی‌شده در نسخهٔ ۰٫۱۸٫۰.** این سند هم تصمیم‌ها و دلیلشان را می‌گوید (ایده‌پردازی، تحلیل، بنچ‌مارک، تحقیق) و هم طراحی نهایی را. تحقیق وب و آزمایش‌های عملی در ۹ اکتبر ۲۰۲۶ (۱۷ مهر ۱۴۰۵) انجام شد. هر ادعای بیرونی با منبع و درجهٔ اعتماد مشخص شده؛ بخش «محدودیت‌ها و آنچه راستی‌آزمایی نشد» را حتماً بخوانید.

## ۱. خلاصه

ادمین یک حساب اینستاگرام و/یا نشانی یک سایت می‌دهد. برنامه با **کد** (بدون AI) آن‌ها را می‌خواند و تحلیل آماری می‌کند، و بعد همان `BUSINESS_BUILD` موجود روی همین شواهد پروفایل ۱۵بخشی را می‌نویسد. از آن به بعد همهٔ کارهای تولید محتوا پروفایل را مثل هر کسب‌وکار دیگر می‌گیرند.

```
حساب اینستاگرام ─┐   خواندن با کد، بدون AI                   AI (فقط در runner)
                 ├─► نسخهٔ متنی + گزارش آماری ─► BusinessReference ─► BUSINESS_BUILD ─► ۱۵ بخش پروفایل
سایت (چندصفحه) ──┘   (INSTAGRAM / WEBSITE)       (ادمین می‌بیند AI چه دید)  (دامنه: فقط منابع من)   «تأییدنشده» تا تأیید انسان
```

چهار تصمیم اصلی (دلیلشان در بخش‌های ۲ تا ۴):

1. **از صفحهٔ وب instagram.com خزش نمی‌کنیم.** صفحهٔ عمومی بدون ورود فقط تعداد دنبال‌کننده می‌دهد (نه بیو و نه کپشن) و `robots.txt` اینستاگرام جمع‌آوری خودکار را بدون اجازهٔ کتبی ممنوع کرده است.
2. **منبع داده اینستاگرام = API رسمی Meta (Business Discovery) یا ورودی دستی** (بیو و کپشن‌های چسبانده‌شده، یا فایل JSON «دریافت اطلاعات» خود اینستاگرام). اسکرپر شخص ثالث ساخته نشد (بخش ۲٫۱).
3. **سایت چندصفحه‌ای خوانده می‌شود** (تا ۱۰ صفحه، با رعایت `robots.txt`)، نه فقط صفحهٔ اصلی. تا قبل از این، منبع «لینک» فقط یک صفحه را می‌خواند.
4. **آمار با کد محاسبه می‌شود، تفسیر با AI.** ریتم انتشار، قالب‌ها، هشتگ‌ها، نرخ تعامل و … را کد می‌شمارد تا مدل مجبور به شمردن نشود؛ ادمین هم همان گزارش را می‌بیند.

### ۲٫۳ ایده‌های دیگری که بررسی شد (برای گام‌های بعد، بخش ۹)

- پست‌های پرتعامل اینستاگرام را به‌عنوان **نمونهٔ سبک** به `BUILD_PROFILE` بدهیم (امروز فقط پروفایل کسب‌وکار ساخته می‌شود، نه پروفایل سبک).
- **تناقض‌یابی با کد** بین سایت و اینستاگرام (نام، تلفن، آدرس) و ثبت در «موارد نیازمند بررسی».
- به‌روزرسانی دوره‌ای و هشدار «سایت یا حساب عوض شده».
- تحلیل رقبا با همین موتور (حساب رقیب را بدهید، آمار را مقایسه کنید). مرز مأموریت: تولید محتوا، نه شنود اجتماعی ([27-strategy-benchmark.md](27-strategy-benchmark.md) هم همین را می‌گوید).
- استخراج رنگ/فونت/لوگوی برند از سایت (Canva این را دارد؛ ما فعلاً از `BUSINESS_ASSET_ANALYZE` استفاده می‌کنیم).

## ۴. تحقیق: آنچه واقعاً یافتم

### ۴٫۱ آزمایش مستقیم روی اینستاگرام (۹ اکتبر ۲۰۲۶)

با یک درخواست ساده (بدون ورود، User-Agent عادی) به `instagram.com/instagram/`:

- پاسخ HTTP ۲۰۰ با HTML حدود ۷۰۰ کیلوبایت.
- `og:description` فقط چنین چیزی است: «تعداد Followers، Following، Posts - See Instagram photos and videos from نام (@نام)». **بیو، لینک بیو و کپشن هیچ‌کدام در HTML نبود** (نه JSON تعبیه‌شده، نه `ld+json`).
- یک نام کاربری ناموجود هم HTTP ۲۰۰ و صفحه‌ای مشابه داد؛ پس با کد پاسخ نمی‌شود فهمید حساب وجود دارد.
- `robots.txt` اینستاگرام با یک اطلاعیهٔ صریح شروع می‌شود: جمع‌آوری داده با ابزار خودکار بدون اجازهٔ کتبی اینستاگرام ممنوع است و باید با «شرایط جمع‌آوری خودکار داده» Meta سازگار باشد.

نتیجه: راه A هم ناکافی است هم مغایر با سیاست اعلام‌شده. (این یک آزمایش یک‌باره از یک IP است؛ اینستاگرام ممکن است برای کاربر واردشده یا IP دیگر چیز دیگری برگرداند. مهم نیست: روش A را به هر حال نساخته‌ایم.)

### ۴٫۲ وضعیت حقوقی اسکرپینگ داده‌های عمومی (درجهٔ اعتماد: متوسط، **مشورت حقوقی نیست**)

- در ژانویهٔ ۲۰۲۴ یک دادگاه فدرال آمریکا در پروندهٔ Meta علیه Bright Data حکم داد که جمع‌آوری داده‌های عمومی فیسبوک و اینستاگرام **بدون ورود به حساب** نقض شرایط استفاده نبوده است؛ Meta بعداً از پرونده دست کشید. حکم محدود است: دربارهٔ داده‌های بدون ورود بود و دربارهٔ حریم خصوصی یا قوانین دیگر چیزی نمی‌گوید.
- در پرونده‌های دیگر، استفاده از **حساب‌های جعلی/واردشده** رفتار متفاوتی دید و Meta علیه آن‌ها اقدام کرده است.
- پس «عمومی بودن» مسئله را حل نمی‌کند: شرایط استفاده، قوانین حریم خصوصی و نحوهٔ استفاده هم مهم‌اند. ما راهی را انتخاب کردیم که این پرسش اصلاً پیش نیاید.

### ۴٫۳ API رسمی Business Discovery (درجهٔ اعتماد: بالا برای شروط؛ متوسط برای فهرست فیلدها)

از مستندات رسمی Meta:

- از طریق **اینستاگرام با ورود فیس‌بوک** و با توکن کاربرِ یک **حساب حرفه‌ای (Business/Creator) خودِ شما** صدا زده می‌شود؛ هدف را با `username` می‌دهید.
- حساب هدف هم باید Business یا Creator باشد؛ حساب شخصی خوانده نمی‌شود. داده برای حساب‌های دارای محدودیت سنی برنمی‌گردد.
- دسترسی‌های لازم: `instagram_basic`، `instagram_manage_insights`، `pages_read_engagement` (و `ads_management` یا `ads_read` اگر نقش از راه Business Manager داده شده).
- رسانه‌ها با صفحه‌بندی مبتنی بر مکان‌نما (`after`) می‌آیند، بدون لینک `next`؛ لایک پنهان‌شده در پاسخ نیست؛ فقط خواندن.
- نسخهٔ API در مستندات ۲۰۲۶ همان `v25.0` بود (قابل تنظیم با `INSTAGRAM_GRAPH_VERSION`).
- **تأییدنشده:** صفحهٔ مرجعی که خواندم فیلدهای `biography`، `website` و `follows_count` را صریحاً فهرست نکرده بود (به فهرست IG User ارجاع می‌دهد). کد اول همه را می‌خواهد و اگر API خطای «فیلد وجود ندارد» داد، با فیلدهای کمتر دوباره تلاش می‌کند (تست دارد). سقف نرخ درخواست در مستندات نبود؛ خطای نرخ به ادمین توضیح داده می‌شود.

### ۴٫۴ فایل «دریافت اطلاعات» اینستاگرام (درجهٔ اعتماد: پایین)

منبع قابل‌اتکایی برای ساختار دقیق `posts_1.json` پیدا نکردم. پیاده‌سازی بر پایهٔ دانش عمومی است: آرایه‌ای از پست‌ها با `media[]` شامل `uri`، `creation_timestamp` و `title` (کپشن). خطای شناخته‌شدهٔ اکسپورت (بایت‌های UTF-8 که به‌صورت Latin-1 ذخیره شده‌اند و فارسی را به `Ø§Ù…` بدل می‌کنند) خودکار اصلاح می‌شود. **این بخش را با یک فایل واقعی امتحان نکرده‌ام؛** اگر فرمت فرق کند، پیام خطای روشن می‌دهد و ادمین می‌تواند کپشن‌ها را بچسباند.

### ۴٫۵ هزینهٔ اسکرپرهای شخص ثالث (فقط برای تصمیم «نساختن»؛ درجهٔ اعتماد: پایین)

از صفحه‌های فروشنده و مقایسه‌های ثانویه: Apify حدود ۱٫۶ دلار برای هزار پروفایل (اکتور رسمی)، Bright Data حدود ۱٫۵ دلار برای هزار رکورد، ScrapeCreators بسته‌های اعتباری حدود ۱ تا ۲ دلار برای هزار اعتبار. هزینه مسئله نیست؛ مسئله ریسک سیاستی، حریم خصوصی و وابستگی به فروشنده است. قیمت‌ها در منابع متناقض بود و **ملاک تصمیم نیستند**.

## ۵. طراحی

### ۵٫۱ تقسیم کار AI و کد

| کد (در درخواست HTTP، بدون AI) | AI (فقط runner، `BUSINESS_BUILD`) |
|---|---|
| خواندن Graph API، خزش سایت، `robots.txt`، sitemap | نوشتن ۱۵ بخش پروفایل از روی شواهد |
| آمار اینستاگرام (ریتم، قالب، هشتگ، منشن، نرخ تعامل، سهم فارسی، فراخوان اقدام) | تفسیر: ستون‌های محتوایی، لحن، پرسونا (برچسب «پیشنهاد») |
| داده ساختاریافتهٔ سایت (JSON-LD: نام، تلفن، آدرس، `sameAs`)، لینک شبکه‌ها، ایمیل/تلفن | استخراج «واقعیت‌های کلیدی» با منبع (تأییدنشده) و `gaps` |
| ساخت نسخهٔ متنی و گزارش (`analysis`) | — |

AI هرگز وب یا اینستاگرام را مستقیم نمی‌بیند؛ فقط **نسخهٔ متنی ذخیره‌شده** را می‌خواند و ادمین هم همان را (با دکمهٔ «مشاهدهٔ متن خوانده‌شده») می‌بیند.

### ۵٫۲ مدل داده

- `ReferenceKind`: دو مقدار تازه `INSTAGRAM` و `WEBSITE`. (enum در Prisma و `packages/shared/src/business.ts` هماهنگ است.)
- `BusinessReference.analysis` (JSON، اختیاری): گزارشی که کد ساخته؛ نوع آن `ReferenceAnalysis` در `packages/shared/src/social.ts` (شناسه `type: 'INSTAGRAM' | 'WEBSITE'`).
  - اینستاگرام: `provider` (`GRAPH`/`MANUAL`)، `profile` (نام کاربری، نام، بیو، لینک بیو، شمارنده‌ها)، `stats` (تعداد پست تحلیل‌شده، بازهٔ زمانی، پست در هفته، آمیزهٔ قالب‌ها، میانگین طول کپشن، ایموجی و هشتگ در هر پست، هشتگ‌ها و منشن‌های پرتکرار، سهم نوشتار فارسی/لاتین، سهم کپشن‌های دارای فراخوان اقدام و پرسش، تعامل، پست‌های پرتعامل).
  - وب‌سایت: `origin`، `name`، `description`، `language`، `pages[]` (نشانی، عنوان، نویسه)، `skipped`، `robotsLimited`، `sitemap`، `schemaTypes`، ایمیل‌ها، تلفن‌ها، `socialLinks[]`.
- migration: `20261012090000_instagram_website_sources`. فقط دو مقدار enum و یک ستون nullable؛ بدون بازنویسی داده.

### ۵٫۳ خواندن اینستاگرام (`social/instagram.service.ts`)

- فقط وقتی `INSTAGRAM_GRAPH_TOKEN` و `INSTAGRAM_GRAPH_USER_ID` تنظیم شده باشد فعال است؛ وگرنه ورودی دستی.
- درخواست: `GET {base}/{version}/{userId}?fields=business_discovery.username(نام){…,media.limit(50){caption,media_type,media_product_type,permalink,timestamp,like_count,comments_count}}`. حداکثر دو صفحه، **۱۰۰ پست**. لایک پنهان «نامعلوم» می‌ماند، نه صفر. توکن فقط در URL درخواست (رسم خود Graph API) است و در هیچ پیام خطا و لاگی نمی‌آید.
- درخواست از همان `MediaFetcherService` می‌گذرد (قواعد SSRF، پراکسی `FETCH_PROXY_URL`، سقف زمان و حجم). متد تازهٔ `getJsonLoose` بدنهٔ خطا را برمی‌گرداند چون Graph API دلیل خطا را در بدنهٔ ۴xx می‌گوید.
- خطاها به توصیهٔ قابل‌اقدام ترجمه می‌شوند: توکن منقضی (کد ۱۹۰)، محدودیت نرخ، نبود دسترسی، «حساب وجود ندارد یا Business/Creator نیست».
- **ورودی دستی:** بیو، تعداد دنبال‌کننده (اختیاری) و کپشن‌ها (جداشده با خط `---`)، یا فایل JSON اکسپورت اینستاگرام که در مرورگر خوانده و به پست تبدیل می‌شود (`parseInstagramExport` در shared). تحلیل آماری برای ورودی دستی هم همان است؛ فقط `provider = MANUAL` و تعامل نامعلوم است مگر ادمین بدهد. داده‌ای که دستی داده شده «خواندن دوباره» ندارد (باید پاک و دوباره اضافه شود).

### ۵٫۴ خواندن سایت (`social/website-crawler.service.ts`, `social/site-parser.ts`)

1. `robots.txt` (گروهی که نام `ContenterBot` را دارد بر `*` برتری دارد؛ طولانی‌ترین قاعده برنده است؛ HTML به‌جای robots نادیده گرفته می‌شود).
2. صفحهٔ شروع (اگر لینک عمیق بود، صفحهٔ اصلی هم). اگر کمتر از ۱۵۰ نویسه متن خوانا باشد (سایت JavaScript یا نیازمند ورود) با پیام روشن رد می‌شود.
3. نامزدها: لینک‌های ناوبری همان سایت + sitemap (یک سطح فهرست‌نقشه). امتیاز با واژه‌های فارسی و انگلیسی (درباره، خدمات، محصولات، تماس، قیمت/تعرفه، پرسش‌ها، تیم، نمونه‌کار، مجله …)؛ صفحه‌های بی‌ارزش (ورود، سبد، حریم خصوصی، فایل‌ها، برچسب‌ها) حذف می‌شوند.
4. حداکثر **۱۰ صفحه** (از جمله شروع) و دو مقالهٔ بلاگ برای نمونهٔ لحن؛ سه درخواست هم‌زمان؛ سقف ۶۰ ثانیه برای کل خزش؛ صفحه‌های نزدیک به تکراری حذف می‌شوند.
5. از هر صفحه متن خوانا (Readability)، و از کل سایت: نام (JSON-LD، `og:site_name`، یا بخش مشترک عنوان صفحه‌ها)، توضیح، زبان، تلفن/ایمیل (لینک‌های `tel:`/`mailto:` و JSON-LD)، آدرس، و لینک شبکه‌های اجتماعی (اینستاگرام با نام کاربری).
6. **میزبان اشتراکی** (شبکه‌های اجتماعی، Google Drive، پلتفرم‌های وبلاگ) به‌عنوان «سایت کسب‌وکار» پذیرفته نمی‌شود (۴۰۰) تا قاعدهٔ `isSharedHost` رعایت شود.

### ۵٫۵ جریان ساخت

`POST /businesses/from-presence` (یا افزودن منبع به کسب‌وکار موجود، زبانهٔ «سایت» و «اینستاگرام» در کارت «منابع مرجع AI»):

1. کسب‌وکار ساخته می‌شود (`origin = SOURCES`)؛ منبع‌ها هم‌زمان خوانده می‌شوند.
2. نام کسب‌وکار اگر خالی بود از سایت/حساب برداشته می‌شود؛ وب‌سایت اگر خالی بود از لینک بیو (به‌جز میزبان اشتراکی).
3. **فقط اگر همهٔ منابع خوانده شدند** `BUSINESS_BUILD` با دامنهٔ پیش‌فرض «فقط منابع مرجع من» در صف می‌رود؛ وگرنه کسب‌وکار با منبع خطادار می‌ماند و ادمین اصلاح می‌کند و خودش ساخت را می‌زند (همان قاعدهٔ `from-references`).
4. اگر سایتی به یک حساب اینستاگرام لینک بدهد که هنوز منبع نیست، کارت منابع «افزودن به منابع» پیشنهاد می‌دهد (از `analysis.socialLinks`؛ بدون ذخیرهٔ حالت اضافه).

### ۵٫۶ اثر در کارهای AI

- منبع‌ها مثل بقیهٔ منابع در `<admin_references>` می‌آیند، با یک **راهنمای خوانش کنار داده** (نه در متن پرامپت، پس نسخه‌های ویرایش‌شدهٔ پرامپت هم دارندش): آمار را همان‌طور نقل کن و دوباره نشمار؛ شمارنده‌ها عکس همان تاریخ‌اند؛ تعامل فقط دربارهٔ همین پست‌هاست؛ از روی آن مخاطب‌شناسی جمعیتی نکن (`KIND_HINT` در `ai/context.ts`).
- `referenceSites()` مرجع `WEBSITE` را مثل `URL` می‌شمارد، ولی `INSTAGRAM` را نه (شبکهٔ اجتماعی میزبان اشتراکی است).
- Docoo/Researcher: `kind` رشته است و افزودن دو مقدار سازگار است؛ `excerpt` فقط بخشی از همان متن عمومی است و کامنت و اطلاعات دنبال‌کنندگان هرگز ذخیره نمی‌شود، پس قاعدهٔ «خروجی بدون افراد» رعایت است.

### ۵٫۷ امنیت و حریم خصوصی

- همهٔ خواندن‌ها از `MediaFetcherService`: فقط http(s)، رد نشانی‌های خصوصی در هر پرش، سقف زمان/حجم، پراکسی. (`INSTAGRAM_GRAPH_BASE_URL` فقط برای تست است.)
- نام کاربری اینستاگرام پیش از ورود به فیلد Graph با `^[a-z0-9._]{1,30}$` بررسی می‌شود (تزریق به `fields` ممکن نیست).
- فقط داده‌های عمومی کسب‌وکار: **کامنت‌ها، دنبال‌کنندگان و پروفایل افراد خوانده یا ذخیره نمی‌شود.** منشن‌های داخل کپشن (هندل عمومی) فقط شمرده می‌شوند. رابط هم همین را به ادمین می‌گوید.
- `robots.txt` سایت‌ها رعایت می‌شود و `User-Agent` همان `ContenterBot` است.
- نقش‌ها: ساخت و افزودن منبع مثل بقیهٔ منابع (`ADMIN`/`EDITOR` با دسترسی به کسب‌وکار)؛ مسیر `instagram-status` برای همهٔ نقش‌ها باز است (فقط یک بولین).
- لاگ ممیزی: `business.create_from_presence`، `business.reference_add` (با `site` یا `instagram: manual`)، `business.update` (پر شدن نام/سایت از منابع).

## ۶. راه‌اندازی API اینستاگرام

بدون آن، همه‌چیز کار می‌کند به‌جز «خواندن خودکار حساب»؛ ادمین بیو و کپشن‌ها را می‌چسباند.

1. یک حساب اینستاگرام **حرفه‌ای (Business یا Creator)** برای خودتان داشته باشید و آن را به یک Page فیس‌بوک وصل کنید (تنظیم Meta، یک‌بار).
2. در Meta for Developers یک اپ بسازید و محصول «Instagram» (API با ورود فیس‌بوک) را اضافه کنید.
3. توکن کاربر با `instagram_basic`، `instagram_manage_insights`، `pages_read_engagement` بگیرید؛ برای استفادهٔ پایدار توکن بلندمدت یا کاربر سیستمی که منقضی نشود (از دانش عمومی: توکن‌های معمولی در حدود ۶۰ روز منقضی می‌شوند؛ جزئیات و نیاز به بازبینی اپ (App Review) برای دسترسی پیشرفته را از مستندات Meta بخوانید، من آن را راستی‌آزمایی نکردم).
4. شناسهٔ حساب اینستاگرام خودتان را (نه نام کاربری) بردارید.
5. در `apps/api/.env`:
   ```
   INSTAGRAM_GRAPH_TOKEN=…
   INSTAGRAM_GRAPH_USER_ID=…
   INSTAGRAM_GRAPH_VERSION=v25.0
   ```
   سپس API را دوباره بالا بیاورید. در رابط، پیام «خواندن حساب از راه API رسمی فعال است» دیده می‌شود.
6. اگر سرور به `graph.facebook.com` دسترسی مستقیم ندارد (ایران)، `FETCH_PROXY_URL` را به پراکسی‌ای بدهید که دارد و `FETCH_PROXY_HOSTS` را شامل `facebook.com` کنید. توجه: یک پراکسی برای همهٔ هاست‌های فهرست‌شده است؛ پراکسی داخل ایران برای سایت‌های `.ir` (docs/13) با پراکسی خارجی برای Meta یکی نیست. اگر هر دو لازم است، فعلاً باید یک پراکسی داشته باشید که هر دو را برساند (محدودیت شناخته‌شده؛ بخش ۷).

مشکل‌یابی: پیام‌های خطا روی منبع (کارت «منابع مرجع AI») می‌آید؛ «توکن رد شد/منقضی» ← توکن تازه؛ «نمی‌تواند این حساب را بخواند» ← حساب شخصی/ناموجود/دارای محدودیت سنی ← ورودی دستی.

## ۷. محدودیت‌ها و آنچه راستی‌آزمایی نشد

**محدودیت‌های شناخته‌شده**

- **حساب شخصی یا خصوصی** با API خوانده نمی‌شود (ورودی دستی). حساب دارای محدودیت سنی هم همین‌طور.
- **سقف ۱۰۰ پست اخیر** و ۱۰ صفحهٔ سایت. آمار فقط دربارهٔ همین نمونه است.
- **سایت‌های JavaScript-محور و پشت ورود** (مثلاً صفحهٔ اصلی digikala.com در آزمایش من صفر نویسه داد) رد می‌شوند و پیام روشن می‌دهند. رندر مرورگر ساخته نشده.
- **سایت‌هایی که درخواست‌های پیاپی را کند یا مسدود می‌کنند** ممکن است فقط یک یا چند صفحه بدهند (در آزمایش، bluebottlecoffee.com یک‌بار ۳ صفحه و بار دیگر ۱ صفحه داد، چون سقف ۶۰ ثانیه تمام شد). نتیجه‌ها همیشه با «تعداد صفحهٔ خوانده‌شده» نمایش داده می‌شوند.
- ریتم انتشار از زمان‌های ثبت‌شده در پست‌هاست؛ پست‌های حذف‌شده یا استوری حساب نمی‌شوند. لایک‌های پنهان نامعلوم می‌مانند.
- نرخ تعامل = (میانگین لایک + کامنت) تقسیم بر دنبال‌کنندهٔ همین لحظه، فقط روی همین پست‌ها؛ شاخص تقریبی است، نه معیار صنعتی.
- یک پراکسی برای همهٔ هاست‌ها (بخش ۶ مورد ۶).
- تشخیص زبان بر پایهٔ سهم حروف است، نه مدل زبانی. «فراخوان اقدام» با فهرست عبارت‌های ثابت فارسی/انگلیسی تشخیص داده می‌شود و ممکن است عبارت‌های دیگر را از دست بدهد.

**آنچه راستی‌آزمایی شد**

- تست واحد: ۴ فایل تازه در `apps/api/src/modules/businesses/social` + `presence.spec.ts` + `packages/shared/src/social.spec.ts` + `apps/web/src/features/businesses/presence.test.tsx` (پارس هندل، اکسپورت و اصلاح متن، آمار، Graph API با پاسخ جعلی از جمله صفحه‌بندی و عقب‌نشینی فیلد، robots/sitemap/JSON-LD، خزندهٔ سایت جعلی، دیالوگ‌ها).
- **آزمون سرتاسری** با API واقعی + PGlite + `AI_PROVIDER=mock`، یک Graph API جعلی و یک سایت جعلی: ساخت کسب‌وکار از حساب و سایت، پر شدن نام و وب‌سایت، رعایت `robots.txt` (صفحهٔ ممنوع هرگز درخواست نشد)، رد لینک پست و میزبان اشتراکی، خطای حساب شخصی با توضیح، ورودی دستی، و رابط (دیالوگ‌ها، اعتبارسنجی، گزارش تحلیل).
- **خزندهٔ سایت روی چند سایت واقعی** اجرا شد (anthropic.com ← ۱۰ صفحه در حدود ۱۰ ثانیه؛ example.com؛ digikala.com ← رد با پیام روشن؛ virgool.io؛ bluebottlecoffee.com). همین آزمایش دو اصلاح را آورد: نام از بخش مشترک عنوان‌ها، و حذف لینک‌های خودِ سایت از «شبکه‌های اجتماعی».

**آنچه راستی‌آزمایی نشد** (پیش از تکیه بر آن‌ها امتحان کنید)

1. **Graph API واقعی:** با توکن و حساب واقعی صدا زده نشد؛ رفتار فیلدها، سقف نرخ و خطاها بر پایهٔ مستندات و پاسخ جعلی است. اولین کار پس از استقرار: یک حساب Business آشنا را امتحان کنید.
2. **مدل واقعی:** ساخت پروفایل با `AI_PROVIDER=mock` اجرا شد. کیفیت بخش‌های نوشته‌شده از روی داده‌های واقعی (و فارسی) را هنوز کسی نسنجیده است. پیشنهاد: روی ۲ تا ۳ کسب‌وکار واقعی اجرا و خروجی را بررسی کنید.
3. **فایل اکسپورت واقعی اینستاگرام** (بخش ۴٫۴).
4. **سایت‌های ایرانی** از این ماشین و با پراکسی امتحان نشد.
5. **ملاحظات حقوقی** (حریم خصوصی، شرایط Meta برای استفاده از Business Discovery در یک ابزار آژانسی): مشورت حقوقی نشده؛ اپ Meta شما ممکن است برای دسترسی پیشرفته نیازمند App Review باشد.

## ۸. API

| متد | مسیر | توضیح |
|---|---|---|
| POST | `/businesses/from-presence` | `{ name?, language, location?, instagram?, instagramManual?, website?, scope, instruction? }` ← `{ businessId, jobId \| null, failed }`. دست‌کم یکی از `instagram`، `instagramManual`، `website` لازم است |
| GET | `/businesses/instagram-status` | `{ graphConfigured }` |
| POST | `/businesses/:id/references` | علاوه بر قبل: `{ url, site: true }` (سایت چندصفحه‌ای)، لینک حساب اینستاگرام (نوع خودکار `INSTAGRAM`)، یا `{ instagram: { handle?, biography?, followers?, posts[] } }` |
| POST | `/business-references/:id/refresh` | برای `INSTAGRAM`/`WEBSITE` دوباره می‌خواند؛ برای اینستاگرام دستی ۴۰۰ |

لینک پست/ریلز/استوری اینستاگرام ← ۴۰۰ با راهنما. لیست منابع اکنون `analysis` هم می‌دهد.

## ۹. گام‌های بعدی (پیشنهاد، اولویت از بالا)

1. **راستی‌آزمایی روی داده و مدل واقعی** (بخش ۷). بدون آن هر ادعای کیفیت بی‌پایه است.
2. پست‌های پرتعامل اینستاگرام ← نمونهٔ سبک برای `BUILD_PROFILE` (پیوند دو نیمهٔ برنامه).
3. تناقض‌یابی با کد بین سایت و اینستاگرام (نام، تلفن، آدرس).
4. پراکسی جدا برای هر گروه هاست (ایران/خارج).
5. به‌روزرسانی دوره‌ای و هشدار تغییر.
6. تحلیل رقبا با همین موتور؛ قبل از آن تصمیم دربارهٔ مرز مأموریت.
7. اتصال OAuth خود صاحب حساب (برای حساب‌های شخصی/خصوصی و آمار عمیق‌تر مثل ریچ).
